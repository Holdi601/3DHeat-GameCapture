# Справка за командите {#command-reference}

Всички команди се пускат от папката на хранилището, с виртуалната среда на проекта:

```bash
.venv\Scripts\python -m heat3d_capture <verb> [options]
```

| Команда | Какво прави |
|---|---|
| [`route`](#route) | Записва само позициите на обиколка във Forza, за да се намери картата във файловете на играта |
| [`telemetry`](#telemetry) | Записва всички канали, по един файл на обиколка, за раздела Състезателен анализ |
| [`laps`](#laps) | Чете библиотеката с обиколки на FH Companion и записва маршрута и пробите на една трасе |
| [`reconstruct`](#reconstruct) | Решава записа офлайн и записва `.glb` |
| [`hud`](#hud) | Чете собствените действия и смъртите на играча, миникарта­та и лентата с убийствата от записа |
| [`locate`](#locate) | Къде е заснет всеки кадър от записа, спрямо изображенията на нивото |
| [`python -m heat3d_capture.ui`](#the-scan-window) | Прозорецът за сканиране |
| [`python -m heat3d_update`](#updates) | Проверява и инсталира актуализация |
| [`python tools/export_onnx.py`](#the-model-converter) | Превръща модела за дълбочина в ONNX |

Когато се стартира като `python -m heat3d_capture`, инструментът първо проверява за по-нова версия
(вж. [Актуализации](updates.md); `HEAT3D_NO_UPDATE=1` го изключва). `--help` след всяка команда показва
нейните опции:

![heat3d_capture --help](../assets/img/cli-help.svg)

Код: [`heat3d_capture/__main__.py`](https://github.com/Holdi601/3DHeat-GameCapture/blob/main/heat3d_capture/__main__.py).

## route {#route}

```bash
python -m heat3d_capture route -o lap [--port 5300] [--seconds 0]
```

Слуша за Forza Data Out и пази само позициите на колата, нищо друго: без модел за дълбочина, без
GPU, без заснемане. Код: [`telemetry/record.py`](https://github.com/Holdi601/3DHeat-GameCapture/blob/main/heat3d_capture/telemetry/record.py).

| Опция | По подразбиране | Значение |
|---|---|---|
| `-o`, `--out` | задължителна | Път на изхода; наставката се сменя, така че `-o lap` записва `lap.npz` и `lap.json`. |
| `--port` | `5300` | Портът, към който играта изпраща (свързан към 127.0.0.1). |
| `--seconds` | `0` | Спира след толкова секунди; `0` работи до Ctrl+C. |

Позиция се пази само докато играта показва състезание (`isRaceOn`), колата се движи по-бързо от
0,5 m/s и е поне на 0,5 m от последната запазена позиция - иначе стоенето в меню при 60 пакета в
секунда би запълнило файла със старта. Времето на всяка проба е състезателното време на играта или
часовникът, ако то е 0. Оформлението се открива точно както при `telemetry` (колата трябва първо да
се движи; вж. [Forza](telemetry-forza.md)).

Веднъж в секунда се извежда колко пакета са получени, колко позиции са запазени и текущата позиция,
или `nothing on port 5300 yet - is Data Out on?`. Маршрутът се **запазва, докато се кара**: на всеки
2 секунди, след като е пристигнала нова позиция (интервалът нараства до двадесеткратното на времето,
което е отнело последното запазване, така че много дълга сесия никога не губи повече от една
двадесета от времето си за запис), и още веднъж, когато записвачът спре по каквато и да е причина -
Ctrl+C, `--seconds` или грешка. Всяко запазване пише `lap.npz.partial` / `lap.json.partial` и после
ги премества върху истинските файлове, така че файловете на диска са винаги цели; при срив или
убит процес се губят най-много последните няколко секунди. Ако нищо не е запазено, извежда как да се
включи Data Out и приключва с код 1.

Изход:

- `lap.npz` - масиви на NumPy `positions` (n x 3, метри), `times`, `speeds` (m/s);
- `lap.json` - чете се без този проект:

```json
{
  "layout": "Horizon dash",
  "samples": 4210,
  "seconds": 182.4,
  "metres_driven": 5120.7,
  "bounds": {"min": [-1200.0, 110.2, 300.5], "max": [-400.3, 160.8, 1400.0]},
  "positions": [[-1180.2, 112.0, 310.4], ...]
}
```

Позициите са собствените световни координати на играта, което ги прави дръжка за намиране на същата
земя във файловете на играта: командата `course` на
[3DHeat GameFiles](https://github.com/Holdi601/3DHeat-GameFiles) взема този JSON и изнася трасето,
по което е минала обиколката.

## laps {#laps}

```bash
python -m heat3d_capture laps                                   # list the courses
python -m heat3d_capture laps "a racing circuit" -o races/circuit [--library DIR] [--margin 80]
```

Чете библиотеката с обиколки, която пази FH Companion, и записва два файла за една трасе: маршрут,
който казва кой парче карта да се изреже от архива на играта, и таблица с всяка проба от всяка
обиколка. Записват се заедно, за да не могат да се разминат. Код:
[`telemetry/fhcompanion.py`](https://github.com/Holdi601/3DHeat-GameCapture/blob/main/heat3d_capture/telemetry/fhcompanion.py).

| Опция | По подразбиране | Значение |
|---|---|---|
| `course` | няма | Име на трасето, търси се свободно. Без него се показва библиотеката. |
| `-o`, `--out` | името на трасето с малки букви, интервалите като `_` | Път на изхода; пишат се `.json` и `.csv` един до друг. |
| `--library` | `%LOCALAPPDATA%\FHCompanion\laps` | Къде са папките на трасетата. |
| `--margin` | `80` | Метри, добавени около обхвата на трасето по x и z в `bounds` на маршрута. |

### Списък {#listing}

Без трасе се извежда броят на папките с трасета и за всяка - броят на файловете с обиколки
(`*.json` на всяко ниво под нея, без `course.json`) и името на трасето, после
`Name one to write it out:  -o <file> <course>`.

### Намиране на трасе {#finding-a-course}

Папките с трасета са наречени `<name> (course_<x>_<z>_to_<x>_<z>)` - старт и финал, закръглени.
Трасето се търси по ред: точното име на папката; частта с името от името на папката, без значение
на главните букви; единствена папка, чието име съдържа текста. Няколко съвпадения са грешка, която
ги изброява.

### Четене {#reading-it}

- `course.json` в папката, когато може да се прочете, дава името и незакръглените старт и финал
  (`Name`, `StartX`, `StartZ`, `FinishX`, `FinishZ`); иначе те идват от името на папката. Трасето се
  води като кръгово, когато старт и финал са на по-малко от 10 m един от друг.
- Всеки друг `*.json` под папката е обиколка (обиколките са няколко нива дълбоко - по клас, кола,
  настройка, етикет - и търсенето е просто рекурсивно). Файловете се четат като UTF-8 с byte order
  mark. Нечетима обиколка се пропуска. Обиколките се подреждат по времето на записа.
- За всяка обиколка: `Lap.samples` (всяка с `X`, `Y`, `Z`, `Speed`, `Throttle`, `Brake`, `Steer`,
  `LatG`, `LongG`, `Gear`, `Clutch`, `HandBrake`, `Puddle`, `Metres`, `Seconds`), и класът на колата,
  поредният номер, перфоманс индексът, секундите на обиколката, дължината, времето на записа и
  стартът от място.

Извежда обобщение (обиколки, проби, най-добра обиколка и нейният клас, обхватът по x/y/z).

### Изход {#output}

**`<out>.json`** - същата форма на маршрут, която пише `route`, така че извличачът на карти приема
и двете: `layout: "fhcompanion"`, `course`, `laps`, `samples`, `bounds` (разширен с `--margin` по x и
z) и `positions` на **най-бързата** обиколка (една линия, а не размазване от всички обиколки).

**`<out>.csv`** - всяка проба от всяка обиколка, по един ред:

| Колона | Значение |
|---|---|
| `course` | име на трасето |
| `lap` | етикет за всяка обиколка: дата и час на записа до минута, и времето на обиколката |
| `car` | поредният номер на колата |
| `car_class` | буква на класа на представянето |
| `pi` | перфоманс индекс |
| `lap_seconds` | времето на обиколката |
| `speed_kmh` | скорост в km/h |
| `x`, `y`, `z` | позиция в света, метри, 3 десетични знака |
| `speed_ms` | скорост, m/s |
| `throttle`, `brake`, `steer`, `lat_g`, `long_g`, `gear`, `clutch`, `handbrake`, `puddle` | както ги записва FH Companion |
| `metres` | разстояние по обиколката, 3 десетични знака |
| `elapsed` | секунди от собствения старт на обиколката, 3 десетични знака |

Стойностите, които не са позиции, се пишат с 4 значещи цифри; позициите имат фиксиран брой десетични
знаци, защото 4 значещи цифри биха притиснали трасето към мрежа от един метър. Имената на колоните са
избрани така, че визуализаторът да картографира файла без да му се казва: `lap` става сесия (две
обиколки на една кола никога не се свързват), `car` - нещото, което се движи, `car_class` - групата,
по която се оцветява, `elapsed` - времевата ос (всяка обиколка се подравнява по собствения си старт).

Накрая извежда подсказка как да се изреже картата от играта с GameFiles, с файла на маршрута или
с изричен правоъгълник.

## reconstruct {#reconstruct}

```bash
python -m heat3d_capture reconstruct lap.mp4 -o lap.glb [--solve-budget 260] [--fuse-interval 0.4] [--model vggt-1b]
```

Възстановява запис офлайн, с пътя на камерата, решен наведнъж от VGGT. Бавно: минути на прозорец
на настолен GPU. Изисква PyTorch, Hugging Face `transformers` и пакета `vggt`, които сканерът не
ползва: те са в `requirements-offline.txt`, а командата проверява за тях след като изведе реда с
лиценза, и предлага да инсталира липсващото (код на изход 1, ако откажете). Пълно описание:
[Офлайн реконструкция](reconstruction-offline.md).

| Опция | По подразбиране | Значение |
|---|---|---|
| `video` | задължителна | Записът. Код на изход 2, ако не съществува. |
| `-o`, `--out` | задължителна | `.glb` за запис. |
| `--solve-budget` | `260` | Най-много кадри, подадени на решавача. Разпределят се по това колко се е преместила картината, не по часовника. Повече е по-точно и много по-бавно. Повече от 400 планирани кадъра се отказват. |
| `--fuse-interval` | `0.4` | Секунди между кадрите, слети в геометрия. |
| `--model` | `vggt-1b` | С кои тежести на VGGT да се решава: `vggt-1b` (`facebook/VGGT-1B`, некомерсиален) или `vggt-1b-commercial` (`facebook/VGGT-1B-Commercial`, със заключване; нужен е достъп, даден от Meta). Редът с лиценза, който се извежда първи, е на този модел. |

Първо извежда реда с лиценза на модела, после всеки етап (`masking`, `planning`, `solving`,
`fusing`, `exporting`) с изминалите секунди и напредък, и накрая обобщение: решени камери, грешка на
затварянето, най-лош шев, бележки и записания файл. Кодът на изход е 0 само ако файл е записан.

## hud {#hud}

```bash
python -m heat3d_capture hud "<recording>.mp4" --game bf6 --player <name> -o out/match [--fps 5] [--start S] [--seconds S] [--metres-per-pixel M] [--cpu]
```

Чете HUD на играта от собствения запис на играча, след мача: собствените действия на играча от
изскачащия прозорец с точки, смъртите и възстановяванията от екраните за падане и разгръщане,
следата от миникартата и лентата с убийствата. Пише `<out>.parquet` (следа и събития, таблица на 3DHeat),
`<out>.events.jsonl`, `<out>.summary.json` и `<out>.map.png` + `.map.json` (мозайката на миникартата
и котвите ѝ за опцията Изображение на карта на визуализатора). Battlefield 6 (`bf6`) е единственият
профил засега.

Нужни са **ffmpeg и ffprobe** в PATH (`winget install Gyan.FFmpeg`, после нов терминал).

| Опция | По подразбиране | Значение |
|---|---|---|
| `video` | задължителна | Записът. |
| `-o`, `--out` | името на видеото | Път на изхода без наставка. |
| `--game` | `bf6` | Чий HUD да се чете. |
| `--player` | налучкано | Името на играча, както го показва лентата с убийствата, търси се свободно. |
| `--fps` | `5` | Проби на миникартата в секунда. |
| `--start`, `--seconds` | цялото видео | Частта от записа, която се чете. |
| `--metres-per-pixel` | няма | Мащабът на миникартата, когато е известен; без него позициите са в пиксели на миникартата. |
| `--cpu` | изключено | Декодиране на процесора, дори когато има карта NVIDIA. |

Пълно описание: [Четене на HUD от запис](hud-video.md).

## locate {#locate}

```bash
python -m heat3d_capture locate build level.glb -o level.db [--game bf6] [--spacing 2.5] [--shadows]
python -m heat3d_capture locate frames recording.mp4 --db level.db -o out/match [--fps 2] [--minimap match.parquet]
python -m heat3d_capture locate eval out/match.parquet --truth poses.parquet [--offset S] [--unit-metres 1]
python -m heat3d_capture locate train level.glb -o level.head.pt [--places auto] [--real out/match.parquet recording.mp4]
python -m heat3d_capture locate refmap level.glb deploy.png -o out/refmap [--mpp 0.5]
python -m heat3d_capture locate minimap recording.mp4 --refmap out/refmap -o out/minimap.parquet [--hud out/match.parquet]
```

`build` извежда ниво от всяко място, на което може да стои играч, и индексира изображенията; `frames`
намества всеки взет кадър от запис спрямо тях, по картината, като резервен вариант се ползва следата
от миникартата на командата `hud`; `eval` сравнява резултат с известни пози на камерата; `train`
обучава модел на местата за една карта върху изображения на нивото (и върху кадри, които вече е
намерил някой пуск), за `build --head`; `refmap` поставя собствената карта на играта (екрана за
разгръщане) върху нивото, а `minimap` чете миникартата на запис спрямо нея, кадър по кадър - това
може да даде предварителната стойност на `frames --minimap`. Нужни са PyTorch и
`requirements-locate.txt`. **Експериментално:** при истински записи засега намира само малка част от
кадрите. Всяка опция, изходите и методът: [Намиране на кадри в ниво](locate.md); пълният списък на
опциите: [Справка за командите](../cli-reference.md).

## Конвертор на модела {#the-model-converter}

```bash
python tools/export_onnx.py [--size small|base|large] [--out PATH] [--side 518] [--opset 17]
```

Превръща контролна точка на Depth Anything V2 във файла ONNX, който изпълнява сканерът. Нужни са
PyTorch, `transformers` и `onnxscript`. Вж. [Дълбочина](reconstruction-depth.md#building-the-model).
